# Requirement Intelligence Subsystem

## Overview

The Requirement Intelligence subsystem is the core domain foundation of Version 3 (Phases 29–42) of the **AI-Driven Software Quality Engineering Platform**. It establishes durable requirement intake, specification identity, lifecycle management, and requirement-to-test traceability.

---

## Architecture & Data Model

### Database Identity vs. Human Requirement Key

The system strictly separates internal database identity from human-readable domain keys:

1. **Database Identity (`id: UUID`)**:
   - Primary key generated by PostgreSQL (`gen_random_uuid()`).
   - Purely technical surrogate key used for relational integrity and foreign keys.
   - Completely decoupled from external requirement formats.

2. **Human Requirement Key (`requirementKey: String`)**:
   - Human-readable canonical key (e.g. `REQ-001`, `REQ-002`, `REQ-003`).
   - Project-scoped unique composite constraint: `@@unique([projectId, requirementKey])`.
   - Immutable once assigned to a requirement.
   - Never modified during requirement updates, renames, or lifecycle state transitions.

3. **Project Requirement Sequence (`ProjectRequirementSequence`)**:
   - Persistent counter table per QA project (`projectId: UUID`, `nextValue: Int`).
   - Transaction-safe atomic counter allocation inside Prisma transaction.
   - Concurrency safe: concurrent creation operations acquire exclusive row updates on `ProjectRequirementSequence` to ensure zero collision or key gaps under parallel intake.

```prisma
model ProjectRequirementSequence {
  projectId String   @id @map("project_id") @db.Uuid
  nextValue Int      @default(1) @map("next_value")
  updatedAt DateTime @updatedAt @map("updated_at")

  project Project @relation(fields: [projectId], references: [id], onDelete: Cascade)

  @@map("project_requirement_sequences")
}

model Requirement {
  id                  String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  projectId           String   @map("project_id") @db.Uuid
  requirementSourceId String?  @map("requirement_source_id") @db.Uuid
  requirementKey      String   @map("requirement_key") @db.VarChar(64)
  title               String   @db.VarChar(255)
  originalText        String   @map("original_text") @db.Text
  type                String   @default("UNKNOWN") @db.VarChar(32)
  priority            String   @default("UNSPECIFIED") @db.VarChar(32)
  status              String   @default("DRAFT") @db.VarChar(32)
  createdAt           DateTime @default(now()) @map("created_at")
  updatedAt           DateTime @updatedAt @map("updated_at")

  project           Project            @relation(fields: [projectId], references: [id], onDelete: Cascade)
  requirementSource RequirementSource? @relation(fields: [requirementSourceId], references: [id], onDelete: SetNull)

  @@unique([projectId, requirementKey])
  @@index([projectId, status])
  @@index([projectId, type])
  @@map("requirements")
}
```

## Key Allocation & Gap Policy

- **Sequence-Based**: Keys are generated from `ProjectRequirementSequence.nextValue` formatted with 3-digit padding (e.g. `REQ-001`).
- **Gap Policy (No Reuse)**: When requirement `REQ-002` is deleted or archived, its key is **never reused**. The next created requirement allocates `REQ-003`, preserving historical audit integrity and avoiding traceability corruption.
- **Custom Keys**: Users may supply custom requirement keys adhering to `/^[A-Za-z0-9_-]{1,64}$/`. If supplied, uniqueness within the project is enforced; if duplicate, the system rejects with `REQUIREMENT_KEY_CONFLICT`.

## Requirement Lifecycle State Machine

Requirements transition through explicit, validated states:

```
               ┌───────────────┐
               │     DRAFT     │
               └───┬───────▲───┘
                   │       │
        Activate   │       │ Move to Draft
                   ▼       │
               ┌───────────┴───┐
    ┌─────────►│    ACTIVE     │◄─────────┐
    │          └───┬───────┬───┘          │
    │              │       │              │
    │   Deprecate  │       │ Archive      │ Restore / Re-activate
    │              ▼       ▼              │
    │   ┌──────────────┐ ┌──────────────┐ │
    │   │  DEPRECATED  │ │   ARCHIVED   │─┘
    └───│              │ │              │─┐
        └───┬──────────┘ └───▲──────────┘ │ Move to Draft
            │                │            │
            └────────────────┘            ▼
                 Archive             [  DRAFT  ]
```

### Allowed Transitions:

- `DRAFT` $\rightarrow$ `ACTIVE`, `ARCHIVED`
- `ACTIVE` $\rightarrow$ `DEPRECATED`, `ARCHIVED`, `DRAFT`
- `DEPRECATED` $\rightarrow$ `ACTIVE`, `ARCHIVED`
- `ARCHIVED` $\rightarrow$ `ACTIVE`, `DRAFT`

### Forbidden Transitions:

- `ARCHIVED` $\rightarrow$ `DEPRECATED` (must be restored to `ACTIVE` first)
- Any attempt to execute a forbidden transition throws structured `INVALID_REQUIREMENT_TRANSITION` error.
- Idempotent transitions (transitioning to the current state) succeed as no-ops without error.

## Security and Project Boundary Isolation

1. **Strict Project Isolation**:
   - All requirement operations (`list`, `get`, `getByKey`, `create`, `update`, `activate`, `deprecate`, `draft`, `archive`, `restore`, `delete`) require a valid `projectId`.
   - Cross-project access by ID or key returns `null` or throws `REQUIREMENT_NOT_FOUND`.
2. **Archived Project Immutability**:
   - If a QA Project is in `ARCHIVED` status, all requirement creation, editing, lifecycle transitions, and deletion requests are rejected with `PROJECT_ARCHIVED`.
3. **Mass-Assignment Protection**:
   - Requirement updates only allow mutating non-identity fields (`title`, `originalText`, `type`, `priority`, `status`). Fields `id`, `projectId`, `requirementKey`, `requirementSourceId`, and `createdAt` are strictly protected.

## Bulk Requirement Intake & Parsing (Phase 32)

Phase 32 introduces deterministic, offline bulk requirement intake from raw pasted text without AI or external dependencies:

1. **Deterministic Parser (`BulkRequirementParser`)**:
   - Pure, local parser engine (`bulk-parser-v1`).
   - Supports:
     - Plain lines (one requirement per line)
     - Numbered lists (`1.`, `2)`, `(3)`, `[4]`)
     - Bullet points (`-`, `*`, `•`, `+`, `–`)
     - Prefixed identifiers (`REQ-01:`, `FR-02 -`, `AUTH_01:`)
     - Indented continuation lines (multiline requirements)
     - Normalizes Windows CRLF and Unix LF
     - Preserves Unicode & international characters (`₹`, `€`, `é`, `日本語`, `हिंदी`)
     - Ignores Markdown headings from candidate list
   - Detects exact/whitespace-equivalent duplicates within the pasted batch (`isDuplicateInBatch = true`).
   - No semantic similarity or AI guessing.

2. **Candidate Preview & Key Allocation Timing**:
   - Parsing produces temporary `RequirementCandidate[]` preview objects with temporary preview IDs (`candidate-1`, `candidate-2`).
   - **Critical Invariant**: Requirement keys (`REQ-001`, `REQ-002`) are **NEVER** allocated during parse or preview.
   - Requirement keys are allocated **ONLY on confirmed import commit**.
   - Canceling a bulk preview consumes 0 requirement keys and creates 0 database records.

3. **Atomic Bulk Import**:
   - Confirmed import executes inside a single PostgreSQL transaction (`prisma.$transaction`).
   - Creates a new `RequirementSource` with `sourceType: PASTED_TEXT` and user-defined or timestamped name.
   - Atomically increments `ProjectRequirementSequence.nextValue` by the candidate count $N$ to reserve keys in bulk.
   - Creates all $N$ requirement records linked to the new source and project.
   - If any failure occurs, the entire operation rolls back atomically (0 requirements, 0 orphan sources).

## SRS & Requirement Document Ingestion (Phase 33)

Phase 33 introduces secure, platform-managed requirement document ingestion for SRS specifications and requirement assets (PDF, DOCX, TXT, MD):

1. **Format Validation & Magic Byte Signatures**:
   - Extension allowlist: `.pdf`, `.docx`, `.txt`, `.md`.
   - File size limit: 25 MB max, non-zero.
   - Deep signature validation:
     - **PDF**: Header starts with `%PDF-` (`0x25 0x50 0x44 0x46 0x2D`).
     - **DOCX**: ZIP container header `PK\x03\x04` with OpenXML package markers, rejecting `.docm`.
     - **TXT / MD**: Plain UTF-8/ASCII text without binary null bytes (`\x00`).
   - Rejects all executable formats (`.exe`, `.app`, `.sh`, `.bat`, `.cmd`, `.ps1`, `.js`, `.jar`, `.docm`, etc.).
   - Path traversal and malicious filename sanitization.

2. **Storage Architecture & File Immutability**:
   - Stored in application-managed storage: `<appDataDir>/storage/documents/<projectId>/<storageKey>`.
   - Storage filename uses UUID identity: `<documentId>.<ext>` (never raw uncontrolled original filename).
   - Set to read-only (`0o444`) to guarantee content immutability.
   - Streaming SHA-256 calculation guarantees integrity and prevents unbounded memory consumption.
   - **Target Repository Independence**: Requirement document storage is strictly isolated and never touches the attached source repository.
   - **Original File Preservation**: The user's external original file is read-only and **never modified or deleted**.

3. **Exact Duplicate Detection (Project-Scoped SHA-256)**:
   - Database enforces project-scoped unique constraint: `@@unique([projectId, sha256])`.
   - Ingestion of an identical file (matching SHA-256) in the same project is rejected with `DOCUMENT_DUPLICATE`.
   - Cross-project duplicate bytes are supported (project-scoped uniqueness).

4. **Atomic Ingestion & Failure Cleanup**:
   - File is staged and hashed in temporary staging directory.
   - Transaction creates parent `RequirementSource` (`sourceType = DOCUMENT`) and `RequirementDocument` record.
   - Staged file is committed to permanent managed storage.
   - On any failure at DB or filesystem level: staging files are removed and DB transactions roll back (no orphan files, no orphan DB rows).

5. **Strict Scope Boundary (Zero Text Extraction)**:
   - Document ingestion strictly establishes document identity, validation, storage, and metadata.
   - Contributes **0 automatic requirements** upon ingestion (extraction belongs to Phase 34+).
   - Zero AI, zero LLM, zero embeddings, zero OCR, zero Playwright.

## Document Text & Structure Extraction (Phase 34)

Phase 34 implements deterministic, local text and structural extraction from managed requirement documents (PDF, DOCX, TXT, MD):

1. **Extraction Pipeline & Architectural Boundaries**:
   - **Pipeline**: `RequirementDocument` $\to$ Managed Bytes $\to$ SHA-256 Integrity Verification $\to$ Format Extractor $\to$ Normalized Text $\to$ Paragraphs/Blocks $\to$ Pages (PDF) $\to$ Headings $\to$ Sections Hierarchy $\to$ Lists $\to$ Tables $\to$ Persistent PostgreSQL `RequirementDocumentExtraction`.
   - **Scope Answers**: _What textual content exists? Where did it occur? What structural context surrounded it?_
   - **Scope Invariant**: Does **NOT** classify sentences as requirements, does not score testability or ambiguity, creates **0 Requirements**, allocates **0 Requirement Keys**, and builds **0 Traceability Links**.
   - **Zero AI / External Services**: 100% deterministic local computation with zero LLM, zero embeddings, zero vector databases, and zero OCR.

2. **Source Integrity & Immutability Enforcement**:
   - Pre-extraction validation recalculates SHA-256 over managed file bytes and compares against `RequirementDocument.sha256`.
   - Discrepancy throws `DOCUMENT_INTEGRITY_MISMATCH`.
   - Missing managed file throws `DOCUMENT_FILE_MISSING`.
   - Original file on external disk is untouched; managed file on disk is untouched (read-only); target source repo is untouched.

3. **Format-Specific Local Extractors**:
   - **Plain Text (`.txt`)**: Deterministic UTF-8 decoding, UTF-8/UTF-16 BOM handling, line ending normalization (`\r\n` $\to$ `\n`), paragraph chunking, character offsets, line bounds, and empty text warnings. `pageNumber` is strictly `null`.
   - **Markdown (`.md`)**: Extracts headings (H1-H6), parent-child section nesting, bullet/numbered lists, code blocks, and GFM markdown tables with cells and rows. `pageNumber` is strictly `null`.
   - **Word Document (`.docx`)**: Safe in-memory ZIP parser with decompression bomb bounds (50 MB limit, 1,000 entries max), ZIP-slip protection (`..` and absolute paths rejected), and safe XML parsing (zero external entity resolution / XXE protection). Extracts headings (`Heading 1-6`), paragraphs, list items (`w:numPr`), and tables (`w:tbl`). `pageNumber` is strictly `null` (never fabricated).
   - **PDF (`.pdf`)**: Deterministic stream parser extracting 1-based physical page numbers (`/Type /Page`), `BT ... ET` text streams (`Tj`, `TJ`, `'`, `"`), font escape decoding, numbered heading detection (`1. Introduction`, `1.1 Architecture`), encryption rejection (`/Encrypt` $\to$ `DOCUMENT_ENCRYPTED`), scanned document warning (`NO_EXTRACTABLE_TEXT` without OCR), and zero active script execution (`/JavaScript` ignored).

4. **Extraction Limits & Resource Protection**:
   - Max plain text size: 10 MB ($10^7$ characters).
   - Max blocks: 50,000 blocks.
   - Max headings / sections: 5,000 each.
   - Max tables: 1,000 tables.
   - Max decompressed DOCX size: 50 MB.
   - Overrun raises `DOCUMENT_EXTRACTION_LIMIT_EXCEEDED`.

5. **Deterministic Re-Extraction & Caching**:
   - Extractor version tag: `document-extractor-v1`.
   - Re-extraction request with unchanged source SHA-256 and extractor version reuses the existing extraction record unless `force = true`.
   - Deleting a `RequirementDocument` cascades in PostgreSQL and deletes its `RequirementDocumentExtraction`.

6. **Renderer UI & Preview**:
   - **Document Extraction Modal**: Displays factual metrics (Pages, Blocks, Headings, Sections, Tables, Lines, Characters), extractor version, and source hash.
   - **Preview Tabs**:
     - _Plain Text Preview_: Monospace text viewer with line numbers and copy-to-clipboard button.
     - _Structure & Headings Tree_: Hierarchical indent tree for H1-H6 headings and page provenance.
     - _Blocks & Elements_: Typed blocks (`HEADING`, `PARAGRAPH`, `LIST_ITEM`, `TABLE`, `CODE_BLOCK`) with line numbers and offsets.
     - _Tables_: Rendered table preview for tabular data extracted from DOCX/Markdown.
     - _Warnings Banner_: Non-fatal extraction warnings (e.g. `NO_EXTRACTABLE_TEXT`, `UNSUPPORTED_ELEMENT`).

## Requirement Candidate Detection & Extraction (Phase 35)

Phase 35 bridges document text and structure extraction (Phase 34) and requirement governance (Phases 29–31) by identifying provisional requirement candidates from structured document extractions using deterministic rule-based analysis:

1. **Pipeline & Architectural Invariants**:
   - **Pipeline**: `RequirementDocument` $\to$ Phase-34 Extraction $\to$ Blocks/Tables/Sections $\to$ Deterministic Candidate Detector $\to$ `RequirementCandidate` Records $\to$ Interactive Review & Editing $\to$ Explicit User Approval $\to$ Atomic Transactional Import $\to$ Real `Requirement` Records.
   - **Candidate vs Confirmed Requirement**: Detected candidates are provisional (`RequirementCandidate`). They are **NOT** confirmed requirements.
   - **Zero AI / External Services**: 100% deterministic local computation with zero LLM, zero embeddings, zero vector databases, and zero external APIs.
   - **Zero Key Allocation Timing Invariant**:
     - Candidate Detection: 0 keys allocated.
     - Candidate Review / Editing / Exclusion: 0 keys allocated.
     - Explicit User Approval + Import: Keys allocated (`REQ-001`, `REQ-002`, ...) using `ProjectRequirementSequence`.
   - **Exact Source Text Immutability**:
     - `sourceText` is preserved exactly as extracted from the document.
     - User edits are saved to `reviewedText`, leaving `sourceText` untouched for forensic traceability.

2. **Deterministic Detection Rules & Scoring**:
   - **Detector Version**: `requirement-detector-v1`.
   - **Explicit Requirement ID (`EXPLICIT_SOURCE_ID`, +5)**: Matches prefixes such as `REQ-001:`, `[FR-12]`, `AUTH-REQ-02:`, `BR-05 -`, extracting the external requirement identifier.
   - **Modal Obligation (`EXPLICIT_SHALL`, +4; `EXPLICIT_MUST`, +4)**: Detects mandatory obligation keywords.
   - **Prohibition Syntax (`PROHIBITION_PATTERN`, +3)**: Detects constraint syntax like `shall not`, `must not`, `may not`, `cannot`, `will not`.
   - **Passive / Explicit Obligation (`REQUIRED_TO_PATTERN`, +3)**: Detects patterns like `is required to`, `are required to`, `required to`.
   - **Agile User Story Pattern (`USER_STORY_PATTERN`, +3)**: Detects `As a <role>, I want <action> so that <benefit>` patterns.
   - **EARS Pattern (`EARS_PATTERN`, +3)**: Detects Easy Approach to Requirements Syntax (`When <trigger>, the system shall <response>`, etc.).
   - **Requirement Table Row (`REQUIREMENT_TABLE_ROW`, +3)**: Identifies requirement matrix tables, extracting ID column and statement columns with row provenance.
   - **Numbered Requirement (`NUMBERED_REQUIREMENT`, +3)**: Identifies hierarchical numbered items (e.g. `3.1.2 The system...`).
   - **Bullet List Requirement (`BULLET_REQUIREMENT`, +2)**: Identifies list items containing obligation verbs.
   - **Section Context (`SECTION_CONTEXT`, +2)**: Identifies items located in sections titled Functional Requirements, Security, Specifications, etc.
   - **Weaker Signals (`WEAK_OBLIGATION_SHOULD`, +1; `OPTIONAL_CAPABILITY_MAY`, +1)**: Identifies recommendations and optional capabilities, attaching `WEAK_OBLIGATION` warnings.
   - **False Positive Elimination**: Rejects pure non-requirement headings, Table of Contents dot leaders, document metadata (version, author, date), boilerplate phrases, and short non-substantive text fragments.
   - **Duplicate Detection**: Identifies exact identical requirement text repetitions within the document and flags `EXACT_DUPLICATE_CANDIDATE` warnings.

3. **Candidate Review Lifecycle & Atomic Import**:
   - **Review Statuses**: `PENDING`, `APPROVED`, `REJECTED`, `IMPORTED`.
   - **Multi-Line Block Handling**: Paragraph blocks containing multiple distinct requirement lines/keys are split into distinct candidates with line-level provenance.
   - **Atomic PostgreSQL Transaction (`prisma.$transaction`)**:
     - Imports all approved candidates in a single transaction.
     - Atomically increments `ProjectRequirementSequence.nextValue` by $K$.
     - Creates $K$ `Requirement` records linked to the document's `RequirementSource` (`sourceType = DOCUMENT`).
     - Updates candidate records to `reviewStatus: 'IMPORTED'` and sets `importedRequirementId`.
     - Zero partial imports on failure; re-import prevention on already imported candidates.

4. **Renderer UI (`RequirementCandidatesModal`)**:
   - Integrated into `RequirementDocumentsList` and `DocumentExtractionModal`.
   - Summary statistics header: Total, Pending, Approved, Rejected, Imported counts.
   - Filter tabs and real-time search bar.
   - Candidate Cards with:
     - External ID badges (`[FR-12]`).
     - Status badges (`Pending`, `Approved`, `Rejected`, `Imported`).
     - Explainable score badges (`Score: 9`) with expandable point breakdown.
     - Exact source text and reviewed text view.
     - Inline text editor.
     - Single-click Approve / Reject / Reset actions.
     - Warning banners (`EXACT_DUPLICATE_CANDIDATE`, `WEAK_OBLIGATION`).
   - Bulk actions: "Approve All Pending", "Reject All Pending", "Re-detect Candidates".
   - Import Confirmation Dialog with explicit impact explanations and confirmation step.

## Requirement Source Provenance & Auditability (Phase 36)

Phase 36 establishes an immutable, forensic audit trail making every Requirement traceable back to its underlying evidence.

### 1. Core Provenance Principles & Invariants

- **Evidence Over Decoration**: Provenance is derived from stable database relationships, cryptographic SHA-256 hashes, and immutable source references—never an editable free-text string.
- **Strict Distinction Between Text Versions**:
  - `sourceText`: Exact immutable text from original evidence.
  - `reviewedText`: Candidate text edited during candidate review (prior to import).
  - `currentRequirementText`: The current content of `Requirement.originalText`.
  - **Edit Invariant**: Updating a requirement via standard Phase-30 editing updates `Requirement.originalText` without mutating `RequirementProvenance.sourceText`.
- **Honest & Truthful Attribution (No Fabrication)**:
  - `MANUAL`: Provenance contains zero fake pages, zero fake sections, zero fake line numbers, and zero document references. Completeness is marked as `MINIMAL`.
  - `PASTED_TEXT`: Persists actual `lineStart`, `lineEnd`, `sourceText`, and `externalRequirementKey` from Phase-32 intake. Completeness is marked as `COMPLETE` when line bounds exist, or `PARTIAL` when absent.
  - `DOCUMENT`: Persists full foreign-key relational linkage: `Requirement` $\to$ `RequirementProvenance` $\to$ `RequirementCandidate` $\to$ `RequirementDocumentExtraction` $\to$ `RequirementDocument` $\to$ `RequirementSource` $\to$ SHA-256 identified source evidence.
  - `pageNumber`: Real page numbers are persisted for PDF ($p \ge 1$). Page numbers for DOCX/TXT/MD are strictly `null` (never fabricated).
- **Source Integrity Verification**:
  - Deterministic cryptographic verification against disk storage at retrieval time:
    - `VERIFIED`: Managed file exists and its calculated SHA-256 matches `sourceSha256`.
    - `MISSING_FILE`: Managed document file is missing from platform storage.
    - `HASH_MISMATCH`: File bytes on disk do not match the immutable SHA-256 fingerprint.
    - `SOURCE_RECORD_MISSING`: Document metadata record is missing from database.
- **Dependency Delete Protection**:
  - Attempting to delete a `RequirementDocument` or `RequirementSource` while active requirements depend on it for provenance is blocked with `DOCUMENT_IN_USE` / `SOURCE_IN_USE`.
- **Project Isolation**:
  - Provenance retrieval and context queries are strictly scoped to the calling `projectId`. Cross-project provenance access is rejected with `PROVENANCE_NOT_FOUND`.
- **Zero AI / External Services**:
  - 100% deterministic local computation with zero LLMs, zero embeddings, zero vector databases, and zero external network calls.
- **Boundary with Phase 41**:
  - Phase 36 preserves **origin source evidence**. Requirement change history and version diffing are part of Phase 41.

## Phase 37: Structured Requirement Representation & Normalization

### Overview

Phase 37 transforms each persisted `Requirement` into a deterministic, machine-usable structured representation without destroying, replacing, or paraphrasing its original text or invalidating provenance.

### Core Architectural Invariants

1. **Original Text Immutability**: `Requirement.originalText` remains strictly intact as the source of truth. Normalization never overwrites `Requirement.originalText`.
2. **Provenance Preservation**: All provenance linkages (`RequirementSource`, `RequirementProvenance`, `documentId`, `candidateId`, cryptographic hashes, line offsets) survive normalization completely unaltered.
3. **1:1 Dedicated Model (`RequirementRepresentation`)**: Structured fields (actor, modality, action, object, conditions, constraints, quantitative values, expected outcome) reside in a dedicated 1:1 table linked to `Requirement`, avoiding clutter on the primary entity.
4. **Pure Determinism**: Normalizer version `requirement-normalizer-v1` is pure, regex-driven, and generates 100% identical outputs across 10,000 runs with zero AI hallucinations or fabricated business logic.
5. **Human Review Protection**: Representations reviewed and corrected by a human (`reviewStatus: REVIEWED`) are protected from silent overwrite during automated re-normalization.
6. **Staleness Detection**: The SHA-256 hash of `Requirement.originalText` is recorded on normalization. If the requirement text is edited later, `isStale` becomes `true` and the status transitions to `STALE` until explicitly regenerated.

### Schema (`prisma/schema.prisma`)

```prisma
model RequirementRepresentation {
  id                          String                     @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  projectId                   String                     @map("project_id") @db.Uuid
  requirementId               String                     @unique @map("requirement_id") @db.Uuid
  normalizedText              String                     @map("normalized_text") @db.Text
  actor                       String?                    @db.VarChar(255)
  modality                    RequirementModality        @default(UNSPECIFIED)
  negated                     Boolean                    @default(false)
  action                      String?                    @db.VarChar(255)
  object                      String?                    @db.Text
  conditions                  Json                       @default("[]")
```

## Phase 38: Requirement Classification & Metadata Enrichment

### Overview

Phase 38 enriches persisted `Requirement` entities with explicit, multi-dimensional, machine-usable metadata (**Category, Subcategory, Domain, Module, Business Capability, Actors, Priority, Risk Level, Criticality, Quality Relevance Flags, Compliance Standards, Bounded Tags, and Explainable Reason Codes**) to support downstream analysis, filtering, and reporting.

> [!IMPORTANT]
> **Key Architectural Statement:**
> Phase 38 classification is deterministic and local.
> Classification is metadata enrichment, not proof that a Requirement is correct.
> Unknown values remain unknown.
> No LLM, embeddings, RAG, or external AI provider is used.
> AI-based Requirement analysis begins in Version 4.

### Core Architectural Invariants

1. **Source Immutability**: `Requirement.originalText`, `Requirement.status`, `Requirement.requirementKey`, `normalizedText`, and `RequirementProvenance` remain strictly unchanged during classification.
2. **Dedicated Metadata Model (`RequirementMetadata`)**: Multidimensional metadata fields reside in a dedicated 1:1 table linked to `Requirement`, avoiding clutter on the primary entity.
3. **Pure Determinism**: Classifier version `requirement-classifier-v1` is pure, regex-driven, and produces 100% identical outputs across 10,000 runs without hallucinations or invented regulations.
4. **Human Review Protection**: Metadata records reviewed and corrected by a human (`reviewStatus: REVIEWED`) are protected from silent overwrite during automated re-classification unless explicitly forced.
5. **Staleness Detection**: The SHA-256 hash of `Requirement.originalText` is recorded on classification. If requirement text is modified downstream, `isStale` becomes `true` until explicitly regenerated.
6. **Conservative Priority & Risk**: User-supplied manual priorities are never overwritten by automated classification. When signals are absent, priority defaults to `UNSPECIFIED` (not `MEDIUM`). Risk indicates consequence of requirement failure, distinct from bug severity.
7. **Compliance Integrity**: Regulations (e.g. GDPR, HIPAA, PCI DSS, SOC 2, WCAG) are recorded only when explicitly referenced in the source text.

- **Categories**: `FUNCTIONAL`, `NON_FUNCTIONAL`, `BUSINESS_RULE`, `INTERFACE`, `DATA`, `COMPLIANCE`, `CONSTRAINT`, `UNKNOWN`.
- **Subcategories**: `PERFORMANCE`, `SECURITY`, `USABILITY`, `RELIABILITY`, `AVAILABILITY`, `SCALABILITY`, `MAINTAINABILITY`, `ACCESSIBILITY`, `COMPATIBILITY`, `PORTABILITY`, `OBSERVABILITY`, `RECOVERABILITY`, `RETENTION`, `INTEGRATION`, `TECHNICAL_CONSTRAINT`, `BUSINESS_LOGIC`.

## Requirement Quality, Testability, Ambiguity & Clarification Analysis (V3 Phase 39)

### Overview

Phase 39 introduces deterministic analysis of requirement quality and testability without modifying requirement records. It assesses clarity, specificity, measurability, testability, completeness, and atomicity, detecting 23 distinct ambiguity and defect patterns while generating actionable stakeholder clarification questions.

### Testability Semantics

- **TESTABLE**: Contains explicit observable behavior (actor, action, object), measurable quantitative constraints, Boolean rejection criteria, or clear state transitions, with 0 fatal errors.
- **PARTIALLY_TESTABLE**: Has observable action but contains non-fatal ambiguity warnings or missing constraints (e.g. undefined timing, vague quantities, open-ended lists).
- **NOT_TESTABLE**: Purely subjective criteria without objective verification criteria (e.g. "The UI shall be user-friendly"), missing observable actions, or contradictory obligations.
- **UNDETERMINED**: Text is empty, too short (< 5 chars), or unintelligible.

### 23 Finding Defect Catalog

1. `VAGUE_TERM`: Context-aware vague qualifiers (e.g. `easy`, `adequate`, `efficient`, `normal` when not part of numeric ranges).
2. `VAGUE_QUANTITY`: Unbounded quantifiers (`several`, `many`, `few`, `some`, `multiple`).
3. `UNDEFINED_TIME_CONSTRAINT`: Subjective latency terms (`quickly`, `fast`, `real-time`, `without delay`).
4. `UNDEFINED_CAPACITY`: Unquantified throughput or traffic (`high transaction volume`, `heavy load`).
5. `SUBJECTIVE_CRITERION`: Purely subjective quality attributes (`user-friendly`, `beautiful`, `clean`, `intuitive`).
6. `UNMEASURABLE_QUALITY_ATTRIBUTE`: Non-verifiable quality statements.
7. `WEAK_MODALITY`: Non-binding modal verbs (`should`, `could`, `might`, `preferably`).
8. `MIXED_MODALITY`: Inconsistent mixing of binding (`shall/must`) and weak (`should/could`) obligations in one requirement.
9. `OPTIONAL_BEHAVIOR`: Explicit optional flags (`may`, `optional`, `can optionally`) assigned INFO severity.
10. `MISSING_ACTOR`: Unspecified triggering agent or user role.
11. `MISSING_ACTION`: No observable system predicate or operation identified.
12. `MISSING_OBJECT`: Action verb lacks target entity.
13. `UNDEFINED_EXPECTED_OUTCOME`: Vague error handling (`handle the error`, `process appropriately`).
14. `UNDEFINED_CONDITION`: Vague prerequisite triggers (`if required`, `when necessary`, `if applicable`).
15. `UNDEFINED_REFERENCE`: References without explicit standard or baseline (`standard timeout`, `default configuration`).
16. `UNRESOLVED_REFERENCE`: Dangling specification cross-references.
17. `OPEN_ENDED_LIST`: Unbounded enumerations (`etc.`, `and so on`, `and more`, `including but not limited to`).
18. `AMBIGUOUS_LOGICAL_OPERATOR`: Ambiguous logical branching (`and/or`).
19. `COMPLEX_NEGATION`: Double negatives or nested negations (`shall not allow ... not to ...`).
20. `COMPOUND_REQUIREMENT`: Non-atomic multiple obligations or chained operations.
21. `UNBOUNDED_SUPERLATIVE`: Idealized superlatives (`fastest`, `best`, `optimal`).
22. `UNDEFINED_COMPARISON_BASELINE`: Comparative terms (`faster`, `better`) lacking comparative baseline ("than X").
23. `UNDEFINED_SCALE`: Unquantified scale expectations (`at scale`, `large number of users`).

## Phase 40: Requirement Dependency, Relationship & Repository Evidence Mapping

Phase 40 connects Requirements to other Requirements and to real source repository evidence deterministically without external AI/LLM, embeddings, or vector databases.

### Subsystem A: Requirement ↔ Requirement Relationships & Graph Analysis

1. **Relationship Taxonomy**:
   - Directional Inverse Pairs:
     - `DEPENDS_ON` ↔ `REQUIRED_BY`
     - `REFINES` ↔ `REFINED_BY`
     - `PARENT_OF` ↔ `CHILD_OF`
     - `CONSTRAINS` ↔ `CONSTRAINED_BY`
   - Symmetric Types:
     - `RELATED_TO`
     - `CONFLICTS_WITH`
     - `DUPLICATES`
     - `OVERLAPS_WITH`
2. **Review Lifecycle**:
   - Automatic detections enter `PROPOSED`.
   - Manual links and user reviews enter `CONFIRMED` or `REJECTED`.
   - Re-analysis strictly preserves confirmed and rejected human decisions.
3. **Deterministic Cycle Detection**:
   - Depth-First Search (DFS) over directional dependency edges (`DEPENDS_ON`, `REQUIRED_BY`, `CHILD_OF`, `PARENT_OF`, `REFINES`, `CONSTRAINS`).
   - Flags `DependencyCycleDto` with canonical paths (e.g. `REQ-001 -> REQ-002 -> REQ-003 -> REQ-001`) without mutating or deleting links.
4. **Self & Cross-Project Invariants**:
   - Self-relationships (`source === target`) are strictly forbidden (`SelfRelationshipError`).
   - Cross-project relationships are rejected (`RequirementNotFoundError`).

### Subsystem B: Requirement ↔ Repository Evidence Mapping

1. **Evidence Taxonomy**:
   - `FILE`, `SYMBOL`, `ROUTE`, `SERVICE`, `COMPONENT`, `DATABASE_MODEL`, `CONFIGURATION`, `TEST_FILE`, `ENTRY_POINT`, `OTHER`.
2. **Deterministic Matching & Scoring**:
   - Tokenizes Requirement text, title, actor, action, object, domain, and tags.
   - Matches against V2 indexed files and symbols (case-normalizing camelCase, PascalCase, snake_case, kebab-case, dot notation).
   - Scoring rules: Exact symbol (+5), multi-token symbol (+4/+5), containing file relevance (+1 to +3), route/endpoint (+4), domain/module (+2), action/object (+1).
   - Score threshold: < 4 dropped, >= 7 strong candidate, capped at top 20 candidates per requirement.
3. **Bounded Secure Source Preview**:
   - Previews are fetched through V2 `SourceContentService` with path traversal protections.
   - Bounded to maximum 50 lines / 2,000 characters.

## Requirement Versioning, Change Detection & Impact Foundation (Phase 41)

Phase 41 makes Requirement evolution historically auditable, deterministic, concurrency-safe, and impact-aware across the quality engineering platform:

### 1. Immutable Historical Snapshots & Monotonic Numbering

- **Immutable Snapshots (`RequirementVersion`)**: Each mutation to a requirement creates an immutable historical version snapshot. Historical version rows are **never** mutated or deleted upon subsequent updates.
- **Monotonic Version Numbering**: Every requirement maintains an integer sequence $1, 2, 3, \dots$ enforced at the database schema level via composite unique constraint: `@@unique([requirementId, versionNumber])`.
- **Atomic Baseline Creation**:
  - Newly created requirements (manual, bulk import, candidate extraction) atomically create `Requirement` + `RequirementVersion` 1 (`changeKind = 'CREATED'`) in the same PostgreSQL transaction.
  - Existing requirements lacking history receive deterministic `BASELINE_CAPTURE` without fabricating speculative historical steps.

### 2. Optimistic Concurrency Control & No-Op Detection

- **Lost-Update Protection**: Requirement updates require clients to supply `expectedVersionNumber`. If `expectedVersionNumber !== currentVersionNumber`, the operation rejects with `REQUIREMENT_VERSION_CONFLICT` (`409`).
- **Canonical Content Hashing (`SHA-256`)**:
  - Deterministically hashes normalized fields (`title`, `originalText`, `type`, `priority`, `status`).
  - **No-Op Protection**: If the computed content hash matches the latest version snapshot, **0 new versions are created** and the operation returns the existing requirement without inflating history.

### 3. Deterministic Text Diff & Structured Change Detection

- **Zero AI Summaries**: Uses a deterministic Longest Common Subsequence (LCS) word and punctuation token diff algorithm.
- **Token Diff Output**: Produces classified tokens (`ADDED`, `REMOVED`, `UNCHANGED`) with adjacent token consolidation.
- **Structured Semantic Shifts**: Deterministically flags:
  - **Quantitative Constraints**: Numerical threshold shifts (e.g. `5 seconds` $\rightarrow$ `2 seconds`).
  - **Modality**: Requirement obligation shifts (`shall`, `must`, `should`, `may`, `will`).
  - **Negation**: Polarity shifts (e.g. `shall allow` $\rightarrow$ `shall not allow`).
  - **Property Transitions**: Title, type, priority, and status changes.

### 4. Non-Destructive Version Restore

- Restoring a past version (e.g. Version 1) does **not** roll back or delete intermediate records (Version 2).
- Instead, it atomically creates a brand-new Version 3 (`changeKind = 'RESTORED_VERSION'`) containing the snapshot content of Version 1, fully preserving linear auditability.

### 5. Deterministic Change Impact Analysis

- **Reverse Dependency Traversal**:
  - When Requirement A changes, all requirements depending on A (e.g. Requirement B where `B DEPENDS_ON A`) are surfaced as `DEPENDENT_REQUIREMENT` impact candidates.
  - Directional `REQUIRED_BY` relationships are also traversed (`A REQUIRED_BY B` $\rightarrow$ B impacted).
- **Hierarchy, Constraints, Conflicts & Evidence**:
  - `CHILD_REQUIREMENT`, `PARENT_REQUIREMENT`, `CONSTRAINED_REQUIREMENT`, `CONFLICT_REVIEW`, `RELATED_REQUIREMENT`, and `REPOSITORY_EVIDENCE`.
- **Bounded Traversal & Cycle Protection**:
  - Traverses transitive dependencies up to depth 3 with cycle detection (`visited` set) preventing infinite loops.
  - Caps candidates deterministically at 50 items.
  - Ignores `REJECTED` relationships and self-edges.
- **Human Review Integrity**:
  - Impact candidates are persisted in `RequirementChangeImpact` with initial status `OPEN`.
  - Engineers review each candidate (`REVIEWED`, `DISMISSED`) with an optional rationale. Existing review decisions are preserved across repeated scans.
